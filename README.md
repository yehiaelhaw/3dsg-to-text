# 3DSG LLM Framework

A framework for working with 3D Scene Graph (3DSG) data — parsing scene graphs into text representations, running LLMs against QA datasets, and evaluating answer quality across representations.

## Overview

The thesis goal is to compare how well LLMs answer questions about a 3D scene when the scene is presented in different text representations (e.g. raw coordinates, json). The framework runs a responder LLM against a QA dataset, scores answers with multiple metrics, and writes results to CSV.

## Project Structure

```
dataset/             # Raw 3DSG .npz files (one per scene)

parsers/             # Convert .npz scene graphs into text representations
  json_parser.py             # Serialize a scene graph to structured JSON text
  raw_coordinates_parser.py  # Serialize a scene graph to raw-coordinates text

utils/
  graph_loader.py    # Load a .npz file into the Building dataclass

evaluation/          # Evaluation framework
  config.py          # EvalConfig dataclass
  core.py            # Data models (Question, EvalRecord, QuestionType, ...)
  runner.py          # Main eval loop — iter_records()
  extraction.py      # LLM-based answer extraction before exact-match scoring
  results.py         # CSV writing — save()
  dataset.py         # Loads .jsonl QA datasets
  scene_loader.py    # Loads scene context files
  llm/               # LLM provider abstraction
    base.py          # LLMProvider interface
    factory.py       # create_provider(backend, model, options)
    ollama.py        # Ollama backend
    gemini.py        # Gemini backend
  metrics/
    reference_based.py  # exact_match, semantic_similarity
    context_based.py    # faithfulness (judge LLM)
  tests/             # Smoke tests (run with python -m evaluation.tests.<name>)

experiments/
  scripts/           # One script per scene — the reproducibility artifact
    Brinnon/
      run.py         # Experiment script for the Brinnon scene
      qa.jsonl       # QA dataset for Brinnon
  results/           # Generated CSV output — gitignored

scene_contexts/      # Scene text files (generated by parsers)
  <scene_id>/
    <representation>.txt
```

## Running an Experiment

Always run from the project root:

```bash
python -m experiments.scripts.Brinnon.run
```

This streams one line of output per question as it completes and writes two CSVs to `experiments/results/Brinnon/`:
- `results.csv` — one row per question
- `aggregate.csv` — grouped by (representation, question_type) with an ALL summary row

## Configuration

Each experiment script constructs an `EvalConfig`:

```python
config = EvalConfig(
    # required
    dataset_path       = "experiments/scripts/Brinnon/qa.jsonl",
    scene_contexts_dir = "scene_contexts",   # root — scene_id is appended automatically
    output_dir         = "experiments/results/Brinnon",
    responder_backend  = "ollama",
    responder_model    = "qwen2.5:7b",
    judge_backend      = "gemini",
    judge_model        = "gemini-2.5-flash",
    # optional
    responder_options  = {"num_ctx": 32768},  # enlarge Ollama context window
    representations    = None,                # None → auto-discover all in scene_contexts/
    repetitions        = 1,
)
```

`scene_contexts_dir` must point to the root (`"scene_contexts"`), not a scene-specific subdirectory.

## Metrics

| Metric | Applicable question types | Method |
|--------|--------------------------|--------|
| `exact_match` | factual, count, yes_no, comparative | Normalised string equality after LLM extraction |
| `semantic_similarity` | factual, descriptive, comparative | Cosine similarity via `all-MiniLM-L6-v2` |
| `faithfulness` | all types | Judge LLM scores 0.0–1.0: is the answer grounded in the scene context? |

### Answer Extraction

Before computing exact_match, the judge LLM extracts a canonical short answer from the model's verbose response (e.g. "There are 7 chairs in Room 16.0." → "7"). Descriptive questions skip extraction and use the full response for semantic similarity.

## Question Types

Defined in `core.py`:

| Type | Description | Metrics |
|------|-------------|---------|
| `factual` | Retrieve a specific entity or value | exact_match, semantic_similarity, faithfulness |
| `count` | Return an integer count | exact_match, faithfulness |
| `yes_no` | Binary answer | exact_match, faithfulness |
| `descriptive` | Open-ended description | semantic_similarity, faithfulness |
| `comparative` | Compare or rank entities | exact_match, semantic_similarity, faithfulness |

## LLM Backends

Supported backends: `ollama`, `gemini`. The factory (`llm/factory.py`) also has stubs for `openai` and `anthropic`.

Set credentials in `.env`:
```
GEMINI_API_KEY=...
```

## QA Dataset Format

Each line in a `.jsonl` file:

```json
{"id": "1", "scene_id": "Brinnon", "question": "...", "ground_truth": "...", "question_type": "factual"}
```

`question_type` is optional — if omitted, it defaults to `descriptive` at eval time.

## Smoke Tests

Run from the project root:

```bash
python -m evaluation.tests.test_ollama_smoke        # Ollama provider — one generation
python -m evaluation.tests.test_gemini_smoke         # Gemini provider — one generation
python -m evaluation.tests.test_dataset_smoke        # dataset loading and field checks
python -m evaluation.tests.test_context_based_smoke  # faithfulness metric end-to-end
python -m evaluation.tests.test_runner_smoke         # full eval loop (3 questions)
python -m evaluation.tests.test_results_smoke        # CSV writing (3 questions)
```

`test_runner_smoke` and `test_results_smoke` use a truncated context window (no `num_ctx` override) so scores will be low — they verify the pipeline runs end-to-end, not answer correctness.
