# 3DSG LLM Framework

A framework for working with 3D Scene Graph (3DSG) data — parsing scene graphs into text representations, running LLMs against QA datasets, and evaluating answer quality across representations.

## Overview

The thesis goal is to compare how well LLMs answer questions about a 3D scene when the scene is presented in different text representations (e.g. raw coordinates, json). The framework runs a responder LLM against a QA dataset, scores answers with two metrics, and writes results to CSV.

## Project Structure

```
  runner.py          # Main eval loop — iter_records()
  results.py         # CSV writing — save(), plots
  dataset.py         # Loads .jsonl QA datasets
  scene_loader.py    # Loads scene context files
  plots.py           # Aggregate and per-question bar charts
  llm/               # LLM provider abstraction
    base.py          # LLMProvider interface
    factory.py       # create_provider(backend, model, options)

  metrics/

  scripts/           # One script per scene — the reproducibility artifact
    Brinnon/

  results/           # Generated CSV output — gitignored

  <scene_id>/
    <representation>.txt
```

## Running an Experiment

Always run from the project root:

```bash
python -m experiments.scripts.Brinnon.run
```

This streams one line of output per question as it completes and writes to `experiments/results/Brinnon/`:
- `results.csv` — one row per question
- `aggregate.csv` — grouped by (representation, question_type) with an ALL summary row
- `ac_comparison.png`, `faithfulness_comparison.png` — bar charts by question type, grouped by representation
- `ac_delta.png` — per-question correctness delta between representations (if ≥2 representations)
- `latency_distribution.png` — response latency per representation
- `faithfulness_vs_ac.png` — 2D scatter of faithfulness vs answer correctness per representation

## Configuration

Each experiment script constructs an `EvalConfig`:

```python
config = EvalConfig(
    # required
    dataset_path       = "experiments/scripts/Brinnon/keyfact-qa.jsonl",
    scene_contexts_dir = "scene_contexts",   # root — scene_id is appended automatically
    output_dir         = "experiments/results/Brinnon",
    responder_backend  = "ollama",
    responder_model    = "qwen2.5:7b",
    judge_backend      = "gemini",
    judge_model        = "gemini-2.5-flash",
    # optional
    responder_options  = {"num_ctx": 32768},  # enlarge Ollama context window
    representations    = None,                # None → auto-discover all in scene_contexts/
    repetitions        = 1,
)
```

`scene_contexts_dir` must point to the root (`"scene_contexts"`), not a scene-specific subdirectory.

## Metrics

| Metric | Applies to | Method |
|--------|-----------|--------|
| `faithfulness` | all questions | Judge LLM scores 0.0–1.0: is every claim in the answer grounded in the scene context? |
| `answer_correctness` | all questions | Weighted fraction of atomic key facts present in the answer (rubric scoring) |

### Key-Facts Rubric Scoring

`answer_correctness` is computed by presenting the judge LLM with the question, the model's answer, and a list of numbered atomic facts. The judge returns YES or NO for each fact. The score is the weighted sum of present facts divided by total weight.

Facts use two weight levels:
- **weight 3** — core answer facts explicitly asked for by the question (room ID, entity name, computed value)
- **weight 1** — supporting details that demonstrate correct reasoning (distances, counts, intermediate steps)

The judge's full YES/NO verdict is stored in `rubric_reasoning` in `results.csv` for post-hoc inspection.

## Question Types

Defined in `core.py`. These are the reasoning-heavy types used in the keyfact datasets — the primary research focus of the thesis.

| Type | Description |
|------|-------------|
| `spatial_reasoning` | Euclidean distance / proximity queries |
| `functional_compatibility` | Affordance-based room suitability |
| `capacity_resource_planning` | Counting or summing resources across rooms |
| `comparative_superlative` | Largest / smallest / most-similar across geometry |
| `semantic_categorical` | Category membership or set difference |
| `anomaly_pattern_detection` | Outliers and structural patterns |
| `dependency_relationship_mapping` | Object-to-room dependency traversal |
| `multi_step_inference` | Multi-condition filtering |
| `conditional_constraint` | Constraint satisfaction queries |
| `multi_step_spatial_reasoning` | Spatial reasoning combined with multi-step logic |
| `conditional_reasoning` | Counterfactual / hypothetical queries |
| `explicit_optimization` | Single-criterion optimisation |

## LLM Backends

Supported backends: `ollama`, `gemini`. The factory (`llm/factory.py`) also has stubs for `openai` and `anthropic`.

Set credentials in `.env`:
```
GEMINI_API_KEY=...
```

## QA Dataset Format

Each line in a `.jsonl` file:

```json
{
  "id": "1",
  "scene_id": "Brinnon",
  "text": "Which Floor B kitchen is closest to a Floor B restroom-type room?",
  "question_type": "spatial_reasoning",
  "key_facts": [
    {"fact": "Room 22.0 [kitchen] is the closest Floor B kitchen to a Floor B restroom-type room", "weight": 3},
    {"fact": "The nearest restroom-type room to Room 22.0 is Room 3.0 [bathroom]", "weight": 3},
    {"fact": "The distance between Room 22.0 and Room 3.0 is approximately 1.74 m", "weight": 1}
  ]
}
```

`question_type` is optional — if omitted it is stored as `None` and appears as blank in the CSV. `key_facts` is required — the dataset loader raises an error if it is missing or empty.

## Smoke Tests

Run from the project root:

```bash
python -m evaluation.tests.test_ollama_smoke        # Ollama provider — one generation
python -m evaluation.tests.test_gemini_smoke         # Gemini provider — one generation
python -m evaluation.tests.test_dataset_smoke        # dataset loading and field checks
python -m evaluation.tests.test_context_based_smoke  # faithfulness metric end-to-end
python -m evaluation.tests.test_rubric_smoke         # rubric_correctness end-to-end
python -m evaluation.tests.test_runner_smoke         # full eval loop (3 questions)
python -m evaluation.tests.test_results_smoke        # CSV writing (3 questions)
```

`test_runner_smoke` and `test_results_smoke` use a truncated context window (no `num_ctx` override) so scores will be low — they verify the pipeline runs end-to-end, not answer correctness.
